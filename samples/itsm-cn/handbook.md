# IT 服务台小助手：中国区实验手册

从一个会回答的模型，做出能查资料、处理工单、遵守权限、积累经验的服务台助手。

**实验版本：2026-10-28 · Launchpad 中国区 · 宁夏区域**

本手册基于 Global 实验的八步主线，重新准备了中国区环境、合成业务数据、Skill、策略和考题。本文保留参考环境的教学案例；新部署必须自行完成各节验收，不继承参考环境的结果。公司、工单和员工资料均为虚构实验数据。

## 概览：八步完成一个服务台助手 {#overview}

| 步骤 | 你要解决的问题 | 完成标志 |
| --- | --- | --- |
| 1 只有模型 | 回答听上去合理，就可信吗？ | 找出未经资料支持的公司流程 |
| 2 加入知识 | 怎样回答公司内部问题？ | 检索到 QD-301、2 小时、AccessHub |
| 3 接入工具 | 怎样查询实时工单？ | 看到真实工具调用和自己的工单 |
| 4 身份权限 | 用户说自己是谁就能查谁吗？ | 本人允许、冒充拒绝、服务台允许 |
| 5 跨会话记忆 | 新会话还能接上之前的工作吗？ | 找回挂起单，真实写入补充信息 |
| 6 观察链路 | 怎样证明工具和策略确实执行？ | 定位模型、工具、参数、结果与耗时 |
| 7 评测优化 | 怎样判断修改真的有帮助？ | 两次评测对应不同版本，逐题比较 |
| 8 经验入库 | 怎样让一次解决变成共同知识？ | 人工审核发布、同步、再次检索成功 |

课堂目标约 90 分钟，部署和评测受排队、模型与索引速度影响。采用“学员动手 + 讲师统一演示策略切换和知识发布”的组织方式；实际等待以控制台状态为准。

## 4 · 身份与权限：真正约束每一次工具调用 {#step4}

普通学员观察测试结果；服务台账号可以编辑策略；本环境中**只有管理员可以切换策略执行方式与 Gateway 附加方式**。讲师使用管理员完成统一切换，避免学员相互影响。

进入 **策略 → itsm_cn_lab_engine**。实验 Gateway 已附加此引擎，并设为“强制 / ENFORCE”。

{{shot:04-policies|本实验的五条策略。基础许可和业务禁止规则需要同时存在。}}

### 两阶段许可与模板按钮

| 模板/阶段 | 含义 | 容易误解的地方 |
| --- | --- | --- |
| 工作区智能体可调用其工具 · A | 给本工作区 Agent 添加工具调用基础许可；工具挂载决定模型可见工具 | 只解决智能体这一关，模板本身不是细粒度白名单 |
| 用户可调用工具 · BT | 允许成员、管理员、系统等主体使用工具 | 只解决代表谁调用这一关 |
| 工具白名单 | 为选中的工具增加 permit 语句 | 若已有宽泛 permit，它不会自动收紧其他规则 |
| 禁止成员使用某工具 | 添加 forbid，管理员除外 | forbid 优先于 permit |
| 自定义 Cedar | 自己写完整规则 | 要使用本引擎的实体、动作和真实工具 schema |

**最终允许，需要阶段 A 和 BT 都允许，且没有适用的 forbid。** 空引擎或只有 forbid 而没有 permit，会默认拒绝。这就是模拟器显示“没有生效策略；默认拒绝”的常见原因。

### requester 必须对应真实用户

实验规则如下；组织者的准备脚本会在目标 Gateway 的工具 schema 上校验后发布。`principal.username` 来自真实登录主体；`context.input.requester` 是模型提交给工具的参数。

本版使用 `AgentCore` 实体和具体工具动作。之前截图中的 `Launchpad::Action::"call_tool"` 属于另一套 schema，不能直接与下面的中国区规则混用。

```cedar
{{requester_policy}}
```

`when` 表示工具参数中的 requester 与真实用户名不同时禁止；`unless` 为配置的服务台账号保留跨用户处理能力。服务台是明确授权的业务账号，不等于所有平台管理员。

{{shot:04-editor|中国区策略编辑器：校验、草稿、生效版本以及执行方式是不同概念。}}

修改文本后需要**保存草稿 → 校验 → 发布**。已发布规则如果仍为“仅记录 / log_only”，不会拦截。管理员把 `itsm_requester_is_self` 的执行方式改为**生效 / active**，并确认 Gateway 附加方式为**强制 / ENFORCE**。

### 在模拟器先判断，再用真实聊天验收

模拟器选实验 Gateway、真实用户主体、调用方 Agent、具体工具 `servicenow___get_ticket`，输入 JSON：

```json
{"requester":"lab02","ticket_id":"RITM0010002"}
```

当主体选 lab01 时，预期 **A 允许、BT 拒绝、最终拒绝**；输入改成本人的 lab01 和 RITM0010001 应允许；服务台主体应允许跨用户查单。模拟器不会真实调用工具，也不会更改工单。

{{shot:04-simulator-deny|开启约束后的模拟结果。检查两个阶段及判定策略，而不只看最上方的红绿标记。}}

真实聊天以 lab02 和服务台身份分别新建会话测试：

| 登录身份 | 请求 | 预期 |
| --- | --- | --- |
| lab02 | requester=lab02，自己的单 | 正常返回 |
| lab02 | requester=lab01，lab01 的单 | 策略拒绝 |
| lab02 | requester=lab02，lab01 的单 | 工具端归属检查拒绝 |
| itdesk01 | 查询 lab01 的单 | 正常返回 |

{{shot:04-live-deny|真实调用被 Gateway 策略拦截的证据。}}

最后一种“自己的 requester + 别人的单号”说明为什么只比较用户名还不够：**后端也必须核验工单归属**。本实验工具已实现此检查。

若只想给单个用户某个工具加许可，可参考：

```cedar
permit (
  principal == AgentCore::User::"lab03",
  action == AgentCore::Action::"servicenow___get_ticket",
  resource
);
```

这是增加该用户的 BT 许可，不会撤销其他宽泛 permit，也不能覆盖 forbid。真正实行单人白名单时，要同时检查现有许可范围；本课程已有成员基线，不需要再添加这条示例。

**验收：** 四种请求均符合上表；最终保持 requester 规则生效。若全部拒绝，检查两条基线；若冒充仍成功，检查是否仅记录、是否附加到正确 Gateway、新会话是否使用最新配置。

## 5 · 跨会话记忆：接着处理之前的工单 {#step5}

本环境使用 launchpad-cn 的自建记忆链路；这里的界面和验证方法按中国区实现编写。运行时写入和召回记忆使用 **Agent + 真实用户**作为范围。新会话不等于换一个 Agent，换 Agent 也不会自动继承原来的记忆。这个范围与记忆控制台的查看权限是两层不同的边界。

这一节以 lab02 演示，保持 lab01 的种子数据不变，供第 7 步评测使用。

第一段新会话：

```text
我是lab02。我有张CRM工单被挂起了，他们要我补充什么？请记住这张单，稍后我要补充材料。
```

应查到 `INC0020002`，说明需要企业微信版本、错误截图和发生时间，并提醒挂起超过 5 个工作日的后果。

{{shot:05-memory-first|第一次会话中真实查到挂起单，建立后续记忆的依据。}}

进入 **记忆**，找到自己的 Agent/用户，等待长期记忆记录出现。抽取是异步的；“聊天结束”并不等于“记忆抽取完成”。查看记忆内容中是否包含工单号或待补材料。

{{shot:05-memory-records|长期记忆记录是跨会话验收的依据，须先等待抽取完成。}}

回到同一个 Agent，点“新会话”，不要在提问里再次写工单号：

```text
我是lab02。上次那张挂起的单，信息我准备好了：企业微信版本4.0.8，发生时间今天上午9点，截图稍后补。帮我回复到单子里。
```

{{shot:05-memory-recall|新会话接上之前的工单，并通过工具补充信息。}}

展开 `add_comment` 调用，确认实际写入 `INC0020002`，工具返回 `in_progress`。这里不能只看到“我已经回复了”就算完成；要查评论和状态。模型还可能提醒版本较低、建议升级 4.1 及以上，这符合知识库。

**验收：** 前一会话有来源、新会话没提供单号但找回了正确工单、补充资料实际写入。另一个账号调用同一 Agent 时，不应自动召回 lab02 的唯一测试标记或个人偏好；同时核对实际使用的 actor，而不是只看自然语言回答。若找不到，检查 Agent 是否相同、长期记忆是否开启及抽取任务是否完成。

**控制台可见性不是个人记忆隐私保证。** 本实验工作区使用共享资源可见性（`shared`），获准查看该 Agent 的成员可以通过记忆控制台/API 查看其记录，包括其他用户范围下的记录。因此，另一账号在记忆页面看到记录，不能记为“控制台隔离通过”，也不能据此认定运行时跨用户召回。

涉及敏感数据时，应由管理员另行设计并验证访问边界。`isolated` 工作区按 Agent 创建者限制资源可见性，可配合各用户独立创建的 Agent 使用；它不是同一共享 Agent 内每个用户记录的私有授权开关。切换后须分别验证页面、列表和按 ID 读取的权限。本实验保持共享教学配置，只使用合成数据。

## 6 · 观察链路：把结果追溯到请求 {#step6}

在 Agent 详情点击 **可观测**，或从左侧进入可观测页面。按 Agent、最近时间和会话筛选，打开刚才的真实查询或补充资料请求。观测数据到达可能有延迟；若暂时没有，稍候刷新，不必重做写操作。

{{shot:06-trace|真实调用链路。根据会话关联模型、工具和耗时。}}

依次核对：

1. 会话和 Agent 是本人的本次实验。
2. 模型发起了哪个工具；聊天中可能带有 `launchpad_gw_` 前缀，策略使用 Gateway 原始工具名，例如 `servicenow___get_ticket`。
3. 参数中的 requester、ticket_id 是否符合刚才的输入。
4. 工具返回的状态、评论与单号是否与回答一致。
5. 从 **策略 → itsm_cn_lab_engine → 决策**查看允许或拒绝，区分 Gateway 的真实请求与模拟器。

{{shot:06-decisions|实验 Gateway 的真实决策记录；模拟结果不能代替真实调用审计。}}

拒绝可能发生在模型调用工具之后；观测中出现一次模型耗时并不代表工具执行成功。`unknown_caller` 是调用方映射问题，业务 forbid 拒绝则应能对应具体规则。

**验收：** 能拿同一条请求解释“谁调用、调用什么、传了什么、返回什么、为什么允许/拒绝、耗时在哪里”。

8 道题全部标记为 `tuning`；另一个数据集的 V01/V02 标记为 `held_out`，不用于生成优化建议。工单题固定使用 lab01 的种子单，评测前不要改动其挂起状态。

### 建立基线

在 **评估任务**新建任务，选完成第 3 步的 Agent 和 `itsm-exam-8-cn`。评估器选：

- GoalSuccessRate：任务目标是否达成。
- Correctness：回答是否正确。
- Helpfulness：是否有用。

提交后等待完成。评测还需等待观测日志可读，再由评委评分；进度停在等待日志不一定是失败。不要反复提交同一任务。

{{shot:07-baseline|基线评测。检查目标 Agent 版本、逐题结果以及失败记录。}}

查看逐题理由，而不只看总分。例如 H04 是否同时说明版本和权限，T02 是否遗漏超时关闭，T01 是否真的调用了工具。

### 生成建议、审核、发布，再评测

从已完成任务进入**优化建议**，选择 **GEPA-lite**，生成系统提示词建议。该流程基于本次评测轨迹反思；不是对模型权重做训练。

{{shot:07-recommendation|优化建议应先审核；保留资料依据、未知不猜和权限边界。}}

人工检查建议是否：

- 保留“内部事实先检索、不知道不猜”。
- 要求实际查单后再报告状态。
- 没有放宽 requester、服务台发布权限或人工审核要求。
- 没有把测试答案硬编码成对所有问题都返回的固定文本。

确认后接受建议，发布 Agent 新版本。等待就绪，用同一份 8 题数据集、同样评委再次运行。再用独立验收集检查没有参与优化的两题。

{{shot:07-compare|同题、同评委、不同 Agent 版本的实际比较。不能承诺每次优化都涨分。}}

{{eval_summary}}

平台功能评测可能采用系统主体，不能据其分数证明普通用户权限隔离。身份隔离以第 4 步真实成员会话及工具端检查为准。

参考环境的基线曾出现一个值得检查的细节：H02 虽获评委通过，实际 VPN 工单的 requester 却是 `EMP-1024`，该轮问题没有提供这个账号。检查参数会发现均分没有揭示的问题。课堂中未知账号应先核实；普通成员也不能靠系统评测的许可绕过第 4 步约束。

参考环境的保留题 V01 核心知识回答正确，但也附带了不匹配的账号建议。这里的“独立”指两题没有参与建议生成；运行仍共用参考 Agent 的长期记忆，并非隔离上下文的质量认证。正式比较身份行为时，应另用干净的评测 Agent/记忆与明确的测试账号。

**验收：** 能明确说出两次运行评了哪个版本，指出改变的行为与逐题依据。分数未升也应如实记录；服务错误不能被包装成答案不正确。

## 8 · 经验入库：从工单到可检索知识 {#step8}

先用普通学员的 Agent 新建会话：

```text
季末最后一天晚上提交拜访记录，CRM提示period locked，怎么办？只检索知识库告诉我已有办法，先不要建单。
```

初始 5 份 KB 文档没有公司的具体补录办法，助手应说明资料不足。通用的“重试、换浏览器”不是已验证的公司流程。

{{shot:08-before-knowledge|入库前：初始知识库缺少 period locked 的公司处理办法。}}

### 服务台生成草稿

退出学员账号，使用组织者分配的 `itdesk01` 登录，打开预建 `itdesk-console-cn`。它挂载两个工具集和第 5 个 Skill `kb-article-from-ticket`。

```text
最近好几个代表季末遇到CRM提示period locked。用period locked、季末、补录这几个关键词检索已解决的工单，至少两份已验证记录相互佐证后，整理成一篇知识文章草稿并保存。排除未经验证的猜测，去掉个人姓名和手机号，把草稿全文及来源单号发给我审核，现在不要发布。
```

应使用 `INC0099001` 与 `INC0099002` 两条已验证来源；排除原因未确认的 `INC0099003`。其中一条历史记录含合成姓名与手机号，正文不得带入这些内容。

参考环境的一次演练中，长会话在保存草稿时遇到 MCP 连接中断。同一失效会话继续重试没有恢复。组织者核实尚未产生文章后，新建会话，复制已核验的精简内容保存成功。遇到相同问题，使用以下恢复输入；如果已有文章编号，应先按编号查看，避免重复创建。

```text
请将以下已核验的知识保存为草稿，不发布。标题：CRM季末period locked补录。正文：地区经理在CRM电脑端开启24小时临时补录窗口，代表在窗口内补录并注明实际拜访日期，再由经理复核。不要修改设备时间。来源工单：INC0099001、INC0099002，均为已解决且verified的工单；不采用原因未验证的INC0099003。不含个人信息。请实际调用draft_article并返回草稿编号。
```

{{shot:08-article-draft|服务台检索来源、排除不确定记录并生成待审核草稿。}}

### 人工审核后发布

确认正文包含：地区经理在 CRM 电脑端开启 **24 小时临时补录窗口**；代表填写**实际拜访日期**；由经理复核；不要改设备时间。核对来源单号且没有个人信息。

同一会话中明确批准：

```text
我已审核这篇草稿：处理步骤与两份已验证来源一致，没有个人姓名和手机号。请发布。
```

{{shot:08-article-published|通过工具发布后的文章编号及知识库数据源位置。}}

草稿不等于发布；发布也不等于立即可检索。本实验发布工具把 Markdown 写入专用 KB 的 S3 数据源。进入 **知识库 → 数据源 → 立即同步**，等待同步 `COMPLETE` 且失败文档为 0。

{{shot:08-kb-synced|同步完成后，确认新文章已经进入知识索引。}}

### 学员再次查询

回到普通学员账号，同一个 Agent 新建会话，再问同样的 period locked 问题。检查它使用了新文章中的已验证处理步骤。

{{shot:08-after-knowledge|入库后：普通学员能检索到审核发布的新知识。}}

学员没有知识发布工具；策略和工具后端也同时要求服务台身份。模拟器中普通用户调用 `servicenow-knowledge___publish_article` 应拒绝，服务台应允许。工具还要求明确的人工审核标记。

**验收：** 检索来源 → 草稿 → 人工审核 → 发布 → 同步 → 再检索完整闭环；未验证记录和个人信息不进入文章。下一轮课程由组织者移除本轮发布文章并重置业务数据，恢复“先不知道、再学会”的对照。

## 收尾：保留可以解释的证据 {#finish}

完成后记录自己的 Agent 名称、版本、一次真实查单会话、一次拒绝会话、记忆写入结果、两次评测及知识文章编号。

不要删除 Default 中的共享资源。组织者按实验包 README 中的重置说明恢复本实验数据。Requester 规则保持生效，Gateway 保持 ENFORCE。

### 常见问题

| 现象 | 下一步 |
| --- | --- |
| Agent 还在部署 | 看部署日志，等“就绪”；第一次部署需要数分钟 |
| 工具报 unknown_caller | 请组织者刷新实验 Gateway 的调用方角色清单 |
| 模型服务暂时不可用 | 留下错误回合，稍后新会话重试；不是业务授权失败 |
| 模拟全部拒绝 | 检查 A/BT 基础许可及生效版本 |
| 冒充仍返回旧信息 | 新建会话，检查实际工具请求及策略执行方式 |
| 新会话不记得旧单 | 确认同一个 Agent/用户，等待长期记忆抽取 |
| 观测暂时没有数据 | 等日志到达并刷新；不要重复提交写操作 |
| 文章发布后搜不到 | 同步对应 KB 数据源，检查失败文档数，再测检索 |

本手册提供验收方法；新部署的截图、日志和实测摘要需由组织者收集。模型输出、耗时及评分每次可能不同。以实际工具返回、策略审计、资料来源和逐题证据为准。

### Findings

1. **Evaluation runs cannot be stopped** (S11, S2, S7, S8). `service.py` drives a run
   `queued → invoking → waiting → evaluating → completed|failed`; `queue.py` has no cancel
   and no route calls `StopBatchEvaluation`. An operator who launches a misconfigured run
   (memory `eval-skills-3p-evaluators` records the live mode where every session fails)
   or who needs the AWS active-batch quota back (5 per account, mirrored by
   `eval_max_concurrent_runs`) has no console action: the run keeps consuming judge
   inference until AWS finishes. AWS supports `StopBatchEvaluation` (202; already-judged
   sessions keep results) and the status enum carries `STOPPING`/`STOPPED`, which the
   poller currently maps to `failed`. Fact: sourced. Inference: partial scores after a
   stop are parseable with `parse_eval_scores` (same result shape).

2. **Runtime versions and endpoints are invisible** (S1, S4, S10, S9). Every re-publish
   creates an immutable version and moves `DEFAULT`; the canary mints named endpoints;
   old Chat sessions stay pinned to the version that first served them. The ledger keeps
   only `row.version`, and nothing lists `ListAgentRuntimeVersions` /
   `ListAgentRuntimeEndpoints` (nor the Harness twins `ListHarnessVersions` /
   `ListHarnessEndpoints`). An operator cannot see whether a re-publish produced v7, what
   `DEFAULT` serves, or whether a failed experiment left `stable`/`treatment` endpoints
   behind. Read-only completion of the agent detail.

3. **Chat's "New session" never ends the previous AgentCore session** (S12, S5, S8).
   `newSession` resets local state; the runtime session lives on until its idle timeout.
   The docs name "user-initiated end", "quota management" and "stalled sessions" as the
   `StopRuntimeSession` cases; post-republish validation needs a fresh session because of
   version pinning (S9). No wrapper exists; the harness has no equivalent op (checked the
   model: no `*Harness*Session*` operation), so the action is runtime-only.

4. **Memory resources can be created and deleted but not edited** (S13, S2). `UpdateMemory`
   supports `description` and `eventExpiryDuration` (7–365). Trap for any implementer:
   `namespaceKeys` on Update "fully replaces the existing set — any key you omit is
   removed", so an edit must either omit the member entirely (verify that omission ≠
   empty set on a live memory) or re-send `GetMemory().namespaceKeys`. The read-only
   guarantee on `memory_console.py`/`memory.py` is structural (S9) and must stay; the
   admin pair is where the mutation belongs.

5. **Gateway rate limits (GA, Aug 2026) are absent from Governance** (S3, S6, S1, S14, S8).
   The pinned 1.17.* model already carries all six operations. Governance manages
   gateways behind the managed tag and already rebuilds `UpdateGateway` payloads; a
   rate-limit panel on the gateway detail (list / create / update entries / delete) would
   complete that surface. Higher difficulty (dimension keys + entries + three metrics)
   and live-traffic risk (rate 0 blocks; fail-open limits blast radius).

6. **SDK drift (finding only, no direction)**: the September 2026 Consent Portal
   operations are not in the pinned `bedrock-agentcore-control` model (grep on
   `Consent` → none), and the release notes call the rate-limit ops `CreateRateLimit…`
   while the model names them `CreateGatewayRateLimit…`. Nothing in the product needs the
   portal yet; revisit on an SDK bump.
